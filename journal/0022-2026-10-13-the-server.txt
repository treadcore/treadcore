                 THE SERVER AS A SERVICE: --LISTEN

                     Paul Richeson, treadcore.org

ABSTRACT

    The GitHub Actions are paused: no tag is pushed, so the packages
    workflow does not run; work goes on along the roadmap. The backlog
    was closed in journal 0009, and step 7 waits for a second machine,
    so this session took step 8. treadcore-server --listen DIR is a
    dedicated host in one lobby, match after match. It takes no seat,
    and the election weighs it with a 10 ms head start and otherwise
    leaves it out altogether. It writes each match's trace and replay
    to DIR and has a plain-HTTP status page. The roadmap's proof clause
    holds on one machine both ways: with the four seats 30 ms from
    everything and the server near, it is elected (worst path 36 to
    39 ms against a seat's 60 and more) and hosts all four; given
    100 ms, it is left out and the four elect among themselves. The
    one thing learned: make exports every variable it declares, so a
    script's ${LAG:-30} never sees LAG unset; the first "near" pass
    was the preference winning on equal links, not the links.

I. INTRODUCTION

    Step 8 of the roadmap: "someone runs one for the group" without
    making it the only option. A peer-elected host stays the default;
    a server is one more candidate, preferred, never required.

II. BACKGROUND

    At the start: rc.6's draft made (journal 0021), Actions paused from
    today, wire version 11, step 7 proven on one machine. Open from
    0021: publish rc.6 no sooner than a day after its tag; that is a
    person's act on GitHub and starts no workflow run.

III. METHOD

    The questions step 8 leaves open were settled from the code:

    1. Seat or not. A headless host already has no seat of its own
       (its seats are the remote peers, then bots); the server keeps
       that, and is not counted toward any seat's --want.
    2. How the election prefers it. A head start off its worst path
       (SERVER_PREFERENCE, 10 ms), not a multiplier: on a LAN every
       path is a millisecond and a multiplier would decide nothing.
    3. What a losing server is. Out: each server is weighed over the
       seats plus itself, each seat over the seats alone, so a server
       is never a relay in someone else's tree. A server that relayed
       would have to stay for a match it is not hosting.
    4. When it probes. Not on its own timer (it would elect alone, or
       on half a matrix): when the first seat's Ping arrives, which is
       when that seat has started probing.
    5. Rejected: one server for every lobby name at once. The
       introducer lists by lobby name and a match is one lobby name;
       one --game per server is the plain reading of "registers as
       hosting under a lobby name".

IV. CHRONOLOGY

     1. Wire version 12: `server` on Beacon, Hello (and the fourth
        field of each known peer), Register, Introduced.
     2. election::elect_among, with three tests: the best-placed
        server hosts; a far one is ignored and never relays, even
        where it would be the shortcut; of two servers the nearer
        hosts.
     3. The lobby: LobbyConfig.server; seats() counts the seats; a
        server never hosts alone, never leaves Discover on its timer,
        never joins a match the introducer names; finish() drops every
        server but the host from the result. Test: three seats and a
        server on loopback all elect the server.
     4. treadcore-server: run_net's host loop moved into host_match and
        routes_from, used by --net and --listen alike; Host::into_socket
        so one port serves every match. listen.rs: the loop, the files
        (match-NNNN, numbered on from what DIR holds), a match no seat
        joins in 15 s given up, the status page (/, /status.json, the
        hosted files by name and nothing else).
     5. lobby-test: LISTEN=near|far. The first near run hosted all four,
        one hash in five logs, the replay matched, and the script still
        died: in near no peer hosts, so `grep -l 'hosting:'` found
        nothing, exited 1, and pipefail ended the script before its
        verdict. Every count's grep now tolerates a zero.
     6. Near and far passed. Reading the votes for this entry: near's
        worst path was 5 ms. make exports LAG=0, so ${LAG:-30} had
        never applied, and the server had won on the preference over
        equal links: a pass, but not the proof. Near now sets 30 ms
        when LAG is 0; rerun: worst path 36 and 39 ms, elected on its
        links.
     7. INTRODUCER=1 LISTEN=near failed its introducer checks: they
        counted peer logs only (the server hosted), and the script had
        handed every seat the server's address, so it was not through
        the introducer alone. Under INTRODUCER the server is now found
        through it or not at all, and the check is that all four seats
        were introduced to the server; passed.
     8. make listen, LISTEN_DIR; README, HOW-TO-PLAY, PROTOCOL, ROADMAP,
        CHANGELOG.

VI. DISCUSSION

    The server took less than the roadmap feared because the lobby was
    already a pure function of a matrix: a server is a flag on the
    wire and a key in the election, and everything after the decision
    is the host that already existed. The two script failures are one
    lesson: a test's harness is code, and a value the harness never
    sees (a zero count, an unset variable that make has set) is where
    it lies. Read the numbers a pass rests on, not only the PASS.
