ABSTRACT

    treadcore began as an afternoon's idea after news coverage of the
    war in Ukraine: tanks on both sides had stopped closing with the
    enemy and started firing indirect under their own drone cover,
    and the tank had become a mobile command post. This entry records
    the first session, in which the brief was written, the battlefield
    technology was researched with sources, and a Rust workspace of
    six crates was written: a deterministic simulation (compiled, six
    tests passing), a wire protocol, a LAN lobby with a pure-function
    host election and relay route, a Brain interface with a rule bot
    and a JSON bot, a headless server that writes readable traces, and
    a Bevy 0.17 client with a telemetry overlay. A Makefile-over-bash-
    over-cargo build system, seven documents, a website for GitHub
    Pages, and a vendor policy were written. The engine build ran a
    6 GB virtual machine out of memory on bevy_ui; the build was
    redesigned around memory (a `make warm` target, jobs sized from
    RAM, a trimmed feature set, profiles without dependency debug
    info). Three signed commits were pushed to github.com/treadcore/
    treadcore. The crates above the simulation have not yet been
    through the compiler; that is the first open problem.

INDEX TERMS

    real-time strategy, indirect fire, counter-UAS, telemetry link,
    deterministic simulation, host election, Dijkstra, UDP, Bevy,
    Cargo workspace, build memory, creation journal.


I. INTRODUCTION

    The question of the day was whether the idea survived contact with
    a text editor: a four-player overhead tank game in which the tank
    is a control centre that deploys technology around itself (drones
    in the air; later, Pillboys on the ground), fires high-calibre
    rounds at coordinates like artillery, and lives or dies by the
    airspace it holds. Secondary questions: could four clients
    negotiate their own server by forming a connectivity route, as the
    brief asked; could the whole thing be Rust with Bevy; and could it
    be built in the small virtual machine it is developed in.

    The answers by evening: yes, yes, and not the way it was first
    tried.

II. BACKGROUND

    A. The brief

    Paul's brief, received at the start of the session, in substance:

      1. A new kind of game, not yet made: a four-player multiplayer
         map.
      2. A server/client protocol; the clients negotiate who is the
         server by forming a connectivity route.
      3. The premise from modern logistics and the modern battlefield:
         each tank's new job is calibrated high-calibre indirect fire,
         and each tank runs a drone crew that defends it from drones,
         as navies put anti-air on most ships. The tank's own drones
         are the new game.
      4. Research: battlefield technology upgrades, drones, battle
         simulation visualisation, HUD overlay telemetry; telemetry
         gives the tank an aircraft-carrier effect over the airspace
         around it; a direct artillery hit still kills it.
      5. Overhead RTS presentation built from that HUD description.
      6. Rust with Bevy (or at least Rust); a build system of bash
         scripts called from Makefiles; make configure, make build,
         make debug with logs captured for AI-assisted development.
      7. A pasted reference document on the 1980s prior art [9]:
         interface, LAN ring networking, map editor, tutorial,
         Brains, and a "WorldLab" proposal for a modern successor.

    Later in the session the brief grew: the project is an "opening
    project" of Paul's afternoon vision after the news; the game is a
    new take on the RTS territory style with pillbox capturing, base
    building and repairing, the tank as the control centre; drones in
    addition to the Pillboys, the tech infantry of the tank's
    personnel.

III. METHOD

    A. Order of operations

    The order was chosen so that the slowest thing (compiling Bevy)
    started first and the most certain thing (the simulation) was
    proven before anything was built on it:

      1. Check the toolchain and the machine.
      2. Research in parallel with scaffolding.
      3. Scaffold the workspace; start `cargo fetch` in the background.
      4. Write and test the simulation.
      5. Start the Bevy dependency build in the background.
      6. Write proto, net, brain, server, build scripts, client, docs
         while it ran.

    Step 5 was the mistake of the day; see Section VI.

    vehicles operating their own interceptor drones. The results and
    their URLs are in documentation/RESEARCH.md and in the References
    below. One check was done on Bevy's version against crates.io

VI. DISCUSSION

    A. The memory lesson

    The engine build failed for a reason that is arithmetic, not
    mystery. Cargo runs one rustc per CPU; Bevy's large crates each
    want a gigabyte and a half at opt-level 3 with debug info; four at
    once is more than the machine has; the kernel swaps; a swapping
    compiler is slower than one compiler. The dev profile as first
    written (dependencies at opt-level 3, Bevy's own recommendation
    for desktop machines) made each rustc larger, and dependency debug
    info made target/ 3.7 GB before the halfway point.

    The redesign is four independent reductions: fewer jobs (sized
    from RAM: min(cpus, (RAM - 1 GB) / 1.5 GB)), smaller crates (no
    debug info for dependencies, opt-level 1 in dev), fewer crates
    (default-features = false, the 2D set), and no LTO in release.
    And one piece of structure: a crate that depends on exactly what
    the window depends on, through a single [workspace.dependencies]
    table, so the engine is built once by `make warm` and found, not
    rebuilt, by everything after. Cargo's artifact cache is keyed on
    (crate, version, features, profile, target); the shared table is
    what makes the two resolutions identical.

    B. The lock lesson

    Two cargo invocations in one workspace do not run in parallel;
    the second waits on the target-directory lock and prints a line
    saying so, which was not seen because its output was redirected.
    The "test that never finished" in step 7 was this. Rule: one cargo
    at a time; never background one and start another.

    C. What went right

    Writing the simulation first and proving it with tests meant every
    later crate was written against a known thing. The one bug the
    tests found (the diagonal bridge) was a map-generation bug that
    would otherwise have appeared as "the bot drove into a river" a
    week later. The determinism test is the keystone: it is what makes
    host authority honest and traces replayable.

    The election as a pure function was the right call. It has four
    tests that run in microseconds, and the lobby's correctness
    reduces to "every peer called it with the same matrix", which is a
    much smaller thing to get right than "every peer ran the same
    distributed algorithm".

    D. On the pair

    The session was Paul directing and an AI pair writing. The pair
    wrote most of the code and all of the first drafts of the
    documents; Paul set the premise, the structure (source/,
    documentation/, vendor/; the journal), the identity (paulr@sdf.org,
    signed), the look (green, white, gold, outlined text), and the
    names (treadcore, Pillboys). The permission system refused two
    git actions (adding a remote, pushing) until Paul said "git push"
    in so many words; that is the system working as intended, and the
    journal records it so a reader does not wonder why the first push
    is a separate step.

VII. OPEN PROBLEMS

    1. The crates above the simulation (proto, net, brain, server,
       client, warm) have not been compiled. The client type-checks
       in the editor's checker; the rest were written after the last
       successful `cargo test` and before the builds were cancelled.
       Expect a round of small fixes.
    2. `make warm` has not been run to completion on this machine.
       Whether 3 jobs fits in 6 GB with the new profiles is a
       prediction, not a measurement.
    3. Bevy 0.17 API assumptions in the client: Time::<Fixed>::
       from_hz, AccumulatedMouseScroll, Projection::Orthographic,
       viewport_to_world_2d returning Result, Gizmos::circle_2d
       taking impl Into<Isometry2d>, Text/Text2d/TextFont/TextColor
       components, LogPlugin filter field. All believed correct; none
       yet compiled.
    4. Whether wgpu finds a usable adapter in this VM (Mesa llvmpipe,
       no virgl; radbeeper's GUI needed a software fallback). The
       warm binary is the test.
    5. Pillboys: control model undecided (a unit moved, or an order
       given). Pillboxes, building, repair, territory: not designed
       beyond CONCEPT.md Section 7.
    6. Client-side prediction, NAT traversal, teams, map files, sound:
       deferred (DESIGN.md).
    7. scripts/ have not been shell-linted (`bash -n`, shellcheck if
       present).
    8. GitHub Pages is not yet enabled in the repository settings; the
       CNAME and index are in place.
